# 第 6 章 AI Algorithm & Agent Technical Realization

本章依据平台当前已上线并完成前后端联调的能力撰写，聚焦个人侧三大 AI 链路（智能简历、模拟面试、学习路径）、企业侧权限差异化复用，以及岗位规则匹配与公平包容机制。对配置中暂未启用的向量检索 / OCR 增强组件、仅停留在界面文案层面的完整盲筛脱敏管线，以及门户中尚未接线的静态壳页面，不作为“已实现交付能力”展开论述。

---

## 6.1 AI 模块需求与业务场景概述

粤港澳大湾区弱势群体跨境就业场景具有高度异质性：求职者语言能力、教育与职业空窗、残障类型与可及岗位形态差异显著，而传统招聘产品往往以“标准简历 + 标准面试 + 关键词搜岗”为主路径，缺少面向低门槛交互与技能优先评价的连续支持。本平台的 AI 能力因此被定位为**就业赋能中间件**：不是替代人力资源决策的黑盒推荐引擎，而是围绕“画像结构化—目标岗位对齐—能力表达—技能补齐—包容匹配”的闭环，向个人用户提供可解释、可编辑、可持久化的智能助手，并向企业用户开放可分级复用的同一能力层。

从业务边界看，平台 AI 服务主要承载于 Python 侧 AI Career Copilot（LangGraph 多 Agent 编排），岗位发布、投递与匹配分计算则由 Node 业务服务完成。前端以个人门户（`individual/`）与企业门户（`corporate/`）为入口，将三类核心工具页与岗位库、申请管理、捐赠法援等业务页串成可感知主链路。该分工保证了：生成式任务由大模型完成语义理解与内容生产，而涉及身份准入、捐赠解锁、岗位硬筛的事务性规则留在可审计的业务层，从而兼顾体验与治理。

个人侧三大 AI 核心链路构成产品主价值。(1) **多语言智能简历**：支持上传/粘贴简历文本抽取结构化画像，结合目标 JD 做缺口追问与定制生成，提供模块润色、四语输出与多格式导出，并支持登录后画像存档与会话内对话式迭代。(2) **AI 模拟面试**：提供题库生成、自定义题目参考答案、程序化交互 Mock（Quick / Full / Specialized），并在结束后给出 Debrief 复盘；题库与互动会话均可持久化后再次加载。(3) **技能学习路径诊断**：复用同一画像与 JD 上下文完成缺口分析，推荐学习资源，并按用户每日可投入学时生成可编辑时间线，支持方案保存。三条链路共享候选人画像与目标岗位上下文，避免用户在各工具间重复上传与重复描述经历。

企业侧 AI 采用**基础能力常开 + Premium 能力捐赠解锁**的差异化设计。企业账号默认可使用发岗、职位管理、公司档案，以及与个人侧同源的智能简历与学习路径工具；交互式模拟面试等高级 HR 能力通过 `has_premium_access` 控制，企业完成捐赠箱捐款后解锁。该设计将公益捐赠与产能工具绑定，使企业在获得面试训练能力的同时支持弱势群体法律援助，符合平台“赋能—可持续”的双重目标。

横切通用需求体现在三方面。其一，**内容多语言输出**：简历、面试反馈与相关检查清单支持简体中文（zh）、繁体中文（zh-TW）、英语（en）与葡萄牙语（pt），以覆盖大湾区内地—香港—澳门跨地投递的语言规范差异；界面 UI 当前以英文为主，与内容生成语言解耦。其二，**跨功能上下文复用**：前端通过统一 JD/画像采集组件与账号画像恢复引导，后端以 Redis 会话态 `CopilotState` 与 MySQL 画像存档打通简历、面试、学习路径三页。其三，**公平导向的匹配机制**：岗位软匹配分以技能重叠、学历档位、经历完备度与 JD 关键词命中为主，不对年龄、性别、残障类型等敏感属性做软分惩罚；岗位侧可配置面向特定群体的开放条件，由硬筛保证“岗位主动包容”而非“隐性歧视打压”。完整“首轮盲筛脱敏”（隐藏姓名照片等身份信息）在产品文案与发岗勾选项中有呈现，当前后端投递链路仍返回完整申请快照，属后续增强项，本章不将其叙述为已闭环算法。

弱势群体适配方面，平台在账号注册与资料页采集残疾类型、职业空窗、收入等推断群体标签字段，并对弱势群体个人实行功能免捐访问；AI 交互侧强调分步澄清、结构化表单与短段落输出，避免一次性长文写作门槛。面试与学习路径均支持“先提交简历与岗位标题、再逐步完善 JD”的柔性输入，以降低银发与残障求职者在文本输入上的认知负荷。上述需求共同约束了后续架构选型：**以可编排的多 Agent LLM 管线为主力，以可解释规则匹配为招聘侧公平抓手，以会话与存档复用降低重复劳动**。

## 6.2 AI 整体技术架构与模型选型

平台 AI 采用三层架构。(1) **基础 LLM 底座**：通过 OpenAI 兼容协议调用 SiliconFlow 上的推理与翻译模型，统一封装于 `backend/models/llm.py`，支持 JSON Schema 约束调用、退化输出检测与语言守卫。(2) **业务插件中间层**：以 LangGraph `StateGraph` 组织 Planner 与各业务 Agent（JD、Profile、Gap、Content、Render、Interview、Question、Answer Evaluation、Learning Path），共享 `CopilotState`；简历专用生成/润色/翻译还提供 REST/SSE 旁路以优化长任务交互。(3) **平台业务接口层**：FastAPI 暴露 `/api/chat`、`/api/resume/*`、`/api/interview/*`、`/api/learning-path/*`、`/api/export/*`；前端 `api-client.js` 负责会话、排队提示与错误降级；认证、捐赠访问、岗位匹配则由 Node `server` 独立提供，AI 问答 Agent 在需要岗位列表时再回调匹配 API。

LangGraph 编排入口为 Planner：先对用户意图做分类，再结合确定性意图覆写与夹紧规则（如学习路径关键词、`forced_intent`、简历编辑 `context_scope`）展开固定执行计划，按条件边路由至对应 Agent 节点，最终经 `respond` 结束。该“LLM 辅助分类 + 规则夹紧 + 固定 Agent 链”的策略，降低了纯自由规划导致的链路漂移，也使 Planner 路由可用离线用例集做确定性评测。会话记忆采用对话轮次裁剪与摘要压缩（`dialogue_memory`），并配合 Redis 会话持久化与 MySQL 业务存档，而不是依赖在线向量库作为主记忆。

大模型选型按任务拆分，避免“单模型包打天下”。主对话与多数 Agent 使用 `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B`（温度约 0.3，`max_tokens` 8192，超时 180s）；简历骨架生成与模块润色使用同系列模型但温度降至约 0.2，以提高结构化稳定性；翻译专用 `tencent/Hunyuan-MT-7B`（温度约 0.1）；面试答案评判引入 LLM-as-judge 配置（低温度、较短 `max_tokens`），用于相关性、 groundedness 与可执行性等维度的二次打分。API 调用链统一为：前端/业务 API → （可选 Redis 排队 `llm_queue`，生产并发建议为 2）→ LangChain `ChatOpenAI` → SiliconFlow。上下文窗口层面，应用侧通过状态压缩（画像 JSON、目标岗位 meta、近期对话摘要）控制 prompt 体积，长任务（整份简历生成）拆为“骨架流式输出 + 模块并行润色”以降低单次调用超时风险。

多语言翻译 / 润色集成逻辑分层实现：生成阶段由 `output_language` 与语言守卫约束主模型直接按目标语种产出；模块级或整页转换则调用翻译模型接口；版式层再按语言切换章节顺序与字体策略（`resume_layout`）。前端简历语言检查清单根据雇主类型与语言做字段合规提示（规则配置驱动）。该方案使“粤港澳四语投递”落在内容对象上，而不强依赖界面四语切换。

关于“统一用户画像数据源”，当前生产路径采用**结构化共享状态**而非在线向量库：`CandidateProfile`（基础信息 + typed facts）与目标岗位上下文写入 Redis `CopilotState`，登录用户可将画像保存到 MySQL 并在简历/面试/学习路径页通过 `profile_record` 恢复到同一会话。Gap 分析、题库生成、学习资源推荐均读取该共享画像与 JD 结构化结果。代码中虽预留 Embedding / Rerank / Chroma / RAG 配置接口，但当前 `enabled: false`，经历—JD 语义向量预匹配不参与在线推理；章节后续缺口识别因此描述为**大模型文本对比 + 规则补充**，不以向量相似度为主算法。

跨模块上下文复用调度由前后端共同完成。后端 `resume_profile_context` / `target_job_context` 负责序列化压缩与字段合并；`PUT /api/resume/target-context` 同步雇主类型、行业与经验级别等 meta；前端 `candidate-jd-setup.js`、`target-job-context.js`、`saved-profile-bootstrap.js` 保证三页录入控件与恢复流程一致。用户一次完成画像与目标岗确认后，后续跳转工具可复用 `session_id`，减少重复上传与重复 Gap 触发。

隐私与公平前置处理在当前版本落实为两层。业务层：匹配软分不引入敏感属性权重；岗位硬筛仅在企业明确配置目标群体开放条件时生效，体现“主动 inclusive hiring”。AI 层：简历语言清单可提示盲筛场景下应注意的表述规范，但不替代招聘端匿名化流水线。后续若启用盲筛，需要在申请查询与企业阅览接口增加字段屏蔽与匿名 ID 映射；本章将已实现部分界定为**技能优先软匹配 + 包容性硬筛 + 弱势群体免捐访问**，与未接线的完整脱敏盲筛作出区分。

## 6.3 个人端核心 AI 子系统设计与实现

### 6.3.1 多语言智能简历生成 Agent

智能简历子系统覆盖“解析—对齐—生成—迭代—导出”全流程，前端页面为 `demo-resume-generator.html`，核心脚本包括 `resume-generator.js`、`resume-optimization-flow.js`、`resume-profile-editor.js` 等；后端以 `profile_agent`、`jd_agent`、`gap_agent`、`content_agent`、`render_agent` 与 `api/resume.py` 协作为主。

**输入解析。** 用户可上传 PDF/DOCX/TXT/Markdown 或直接粘贴文本。文件经 `file_parser` 抽取纯文本：PDF 当前采用 pdfplumber 文本层提取（配置中的 DeepSeek-OCR 路径保留但未启用）。文本进入 `/api/chat` 且 `forced_intent=upload_profile` 时，由 `profile_agent` 调用主 LLM 与画像抽取提示词，输出 `CandidateProfile`：包含姓名联系方式等 `profile_basic`，以及 internships / projects / work / education / skill 等 typed `facts`。若用户后续回答澄清问题，走 `profile_patch` 意图做增量事实修补，避免每次全量重抽导致字段抖动。

**JD 对齐与交互式补全。** JD 可粘贴完整描述、由标题生成草稿，或经 `jd_agent` 解析为技能、职责与要求结构化对象，并可命中 JD 缓存复用。前端优化流在生成前触发 Gap 分析：`gap_analysis_core` 让 LLM 对比 enriched JD 与 profile，产出缺口列表、建议追问与可能需弱化/删除的经历提示；系统再用规则补充量化表达类追问，并对删除建议做安全过滤（例如禁止仅因页数理由删除教育经历）。用户在弹窗中分步作答后，系统基于 `resume_clarification_targets` 定位受影响模块，执行增量润色而非整份重生成，从而降低等待时间并保留用户已确认内容。该交互特别适合经历碎片化、需引导补充量化结果的弱势群体用户。

**多语言生成、润色与翻译。** 简历生成采用模块化策略：先由简历生成 LLM 产出整体骨架（摘要、模块顺序与软约束），再对经历等模块并行调用润色例程；`/api/resume/generate-stream` 以 SSE 推送进度，改善长任务可感知性。目标语言写入 `render_config.language ∈ {zh, zh-TW, en, pt}`，生成过程受语言守卫约束；用户也可对单模块执行 Polish，或调用 Hunyuan 翻译模型完成模块/整页转换。版式渲染由 `render_agent` 套用 HTML 模板，并结合页数检测与字体压缩策略，导出端支持 PDF（WeasyPrint）、DOCX、HTML 等（`api/export.py`）。四语适配不仅是字符串翻译，还包括章节顺序与合规字段检查随雇主类型变化，以贴近三地简历阅读习惯。

**对话式迭代与历史版本。** 会话内可将 `context_scope` 限定为简历编辑，使 Planner 只路由到内容修改、语言转换、排版与问答等安全意图，防止误触发整链重跑。前端 Profile 编辑器提供可视化字段修改与模块操作；账号侧支持画像保存、历史列表与恢复。生成后的草稿、快照与检查清单由简历 API 维护，用户可在同会话中继续对话修订。该设计把“一次生成”升级为“可审计的迭代工作流”。

**弱势群体画像字段适配。** 画像与账户资料可保留空窗期、残障相关说明等字段，但输出规则强调以可迁移技能与成果表达为主：Gap 追问引导补充可验证成就与工具能力；语言清单提示避免不必要的敏感信息披露；生成提示约束模型在目标 JD 框架下重组经历，而不是扩写虚构内容。总体算法范式可概括为：**LLM Prompt 编排 + JSON 契约校验 + 规则后处理**，不以在线 RAG 检索为简历定制前提。

### 6.3.2 AI 交互式模拟面试 Agent

面试子系统前端为 `demo-interview.html` / `interview-prep.js`，后端由 `interview_agent`、`interactive_interview_agent`、`answer_evaluation_agent`、`question_agent` 与 `api/interview.py` 构成，程序结构配置于 `tools/interview_program.py`。

**题库分层与程序版本。** 题库模式根据候选人画像与目标岗位生成问题集，固定包含自我介绍等基础题，并结合岗位关键词推断 track，叠加通用筛选题与岗位专项题。程序版本分为：Quick（约 30 分钟量级，合并初筛与终面节奏）、Full（多轮：初筛—专业/技术—总监/HR 终面）、Specialized（技术深挖 / 谈薪协商 / 简历深挖等单阶段专项，轮次上限由配置约束）。该分层把“完整模拟”与“碎片化专项练习”都纳入同一产品入口，便于时间受限的求职者选择轻量路径。

**自定义题目与多轮交互。** 自定义模式允许用户粘贴或录入自有题目，由 Agent 生成参考答案与答题要点，适合针对特定公司真题做准备。交互 Mock 模式则：开局预生成银行队列→用户逐轮作答→异步反馈/必要时追问→结束时汇总 Debrief。前端与后端通过 `/interactive/start|turn|poll|end` 与状态查询接口协同，轮询机制用于消化异步评判延迟。语言方面支持问题与反馈语种选择，并与简历侧四语设定保持一致的使用习惯。

**Debrief 评价算法。** 单题评价由主评模型给出结构化反馈，并可叠加 judge 模型在相关性、事实 groundedness、行动可执行性等维度打分，形成“主评叙述 + 量规打分”的混合结果。整场结束后的 Debrief 汇总能力表现、话术改进建议与后续练习方向，前端可渲染报告文本。评价强调可操作建议，而非仅给笼统分数，以服务真实备考改进。

**持久化与加载。** 登录用户可将题库记录与互动面试会话（含 debrief）保存到账号，并提供 history / 按 ID 加载接口；前端在保存前提示确认，并在列表中恢复。与简历模块相同，面试页复用 `candidate-jd-setup` 与已存画像引导，使用户不必重新解析简历即可开面。算法层面，面试链同样是 **LLM JSON 生成 + 规则化阶段队列**，不依赖向量题库检索。

### 6.3.3 技能缺口诊断与个性化学习路径引擎

学习路径页 `demo-learning-path.html` / `learning-path.js` 对应 `learning_path_agent` 与 `api/learning-path.py`。引擎输入仍是共享的候选人画像与目标 JD；若会话中已有 Gap 结果则直接复用，否则调用与简历侧同源的 `run_gap_analysis`。

**缺口识别。** 在当前未启用 Embedding 时，系统不运行经历—JD 向量相似度批处理，缺口完全由 LLM 对照结构化 JD 与 profile JSON 推理，再由规则补充量化类缺口并过滤不合理删除建议。该方法牺牲了细粒度语义检索召回，但换取了部署简单、结果可解释（缺口条目对应自然语言理由），并与简历澄清追问保持一致口径，避免“简历一套缺口、学习路径另一套缺口”的体验分裂。

**资源匹配与学时规划。** Analysis 阶段在缺口列表之上调用资源推荐提示词，让模型给出课程/练习/项目类轻量资源及估时；当用户消息包含每日学时与时间线意图时，系统先按数学式估算总周数（总学时对每日学时与每周天数取整上入），再由 LLM 划分阶段目标、活动与检查点。用户可在前端直接编辑阶段字段，并通过 `PUT /timeline` 与 `POST /save` 持久化方案，支持历史加载。资源匹配规则偏向可执行、短周期、与柔性就业技能相关的学习单元，使空窗期较长或需边学边求职的用户能够形成“可勾选”的行动清单。

整体上，学习路径引擎是简历 Gap 的下游消费方，通过共享状态把“发现问题—生成简历表达—补齐技能”串联为闭环，而不是独立训练的推荐模型。

## 6.4 岗位智能匹配与公平包容算法

岗位浏览与投递前端为 `demo-jobs-database.html`、`apply.html`、`my-applications.html`、`friendly-employers.html`，匹配计算位于 Node `match.service.js` 与岗位/申请控制器，不属于 Python Agent 主图。该划分使匹配分成为稳定、可单测的规则服务，并供面试问答 Agent 在需要时拉取“已匹配岗位列表”做自然语言解说。

**岗位结构化特征。** 企业发岗时填写技能、描述、学历与包容性条件（年龄区间、性别开放、残障开放、职业空窗友好等）。匹配前先取活跃岗位，并基于用户资料与岗位 `target_criteria` 做硬筛：仅保留用户符合岗位主动开放条件的职位。岗位技能来自显式 skills 字段，并从描述中抽取有限中英词元作为补充标签，覆盖客服、远程运营、数据标注等柔性岗位常见表述，但标签体系是字符串集合而非深度本体。

**求职者技能映射。** 简历快照或结构化 content_json 中的 skills、facts（skill / internship / project / work / education）与摘要文本被规范化为小写技能集合；经历成就文本会做简单切词扩充。该过程是符号级映射，目标是与岗位技能集合计算重叠，而不是输出连续语义向量。

**匹配分加权（0–100）。** `scoreJobResume` 将分项加权：技能子串重叠上限约 50；学历档位匹配上限约 15；经历条数启发式上限约 20；JD 关键词落在简历文本上限约 15。投递时写入 `match_score` 与 `match_reasons`，列表页按匹配分排序展示。友好雇主列表侧对企业“弱势群体友好”属性做筛选/露出；申请排序在业务上可对弱势群体申请人给予优先呈现，以强化包容招聘激励。需要强调：这里的“AI 逻辑”主要体现在上游简历结构化与可选的自然语言说明，**核心分数是可审计规则**，便于向求职者解释“为什么匹配/不匹配”。

**公平机制与盲筛边界。** 软分维度刻意聚焦技能、学历、经历完备度与 JD 关键词，避免把年龄、性别、残障类型直接写入打分公式，从而实现“技能优先”的评价取向。硬筛则服务于企业声明的 inclusive 岗位，而不是把弱势群体挡在通用岗位之外。至于完整盲筛——在企业初筛阶段隐藏姓名、照片、人口统计信息，仅展示技能雷达/匹配理由——目前更多体现在产品说明与部分 UI 选项，申请数据接口仍提供完整快照。因此，本章将已实现公平能力概括为：**技能优先规则匹配 + 包容岗位硬筛 + 友好雇主与弱势群体优先策略**；匿名盲筛流水线列为后续工程扩展，不应夸大为已上线算法模块。

## 6.5 企业端 AI 能力差异化实现

企业门户复用个人侧同一套 AI Career Copilot 前端页面与后端会话能力，而不是另外部署企业专属大模型。`corporate/portal.html` 在 HR Tools 区挂载智能简历、模拟面试、学习路径入口，并内嵌职位管理与仪表盘统计。公司档案与发岗表单收集包容性岗位条件、目标群体与匹配相关开关，使企业侧数据直接进入 6.4 所述硬筛与列表逻辑。

**免费基础工具。** 对企业账号，`access.service` 规定基础访问 `has_access` 恒为 true：企业可发岗/改岗、管理 My Jobs、编辑公司档案、使用法律援助相关入口，并免费打开智能简历与学习路径（与个人页同源）。仪表盘展示职位与申请统计，不额外依赖 Premium。该分层降低中小企业试用门槛，使“先发包容岗、再用 AI 打磨岗位与样本简历”成为低成本路径。

**Premium 模拟面试解锁。** 企业高级能力由 `has_premium_access` 控制：未捐赠企业在门户面试入口带有 `data-require-premium-access`，前端 `platform-access.js` 拦截并引导至捐赠页；完成任意金额捐赠后 `DonationModel` 计数生效，Premium 解锁。弱势群体个人则免捐且同时拥有基础与 Premium 访问；非弱势群体个人需捐款解锁平台功能。权限服务与模型推理解耦——捐赠只改变访问布尔量，不改变模型版本或提示词，保证合规审计简单。

**权益展示与捐赠页。** 企业捐赠页与个人捐赠页复用捐赠/法援前端逻辑，展示捐赠统计、解锁说明与法律援助入口。权益文案以产品配置与 i18n 文案呈现为主，而非再调用大模型实时“生成权益广告文案”。设计重点是清晰传达“捐赠→法律援助资金池→企业 Premium 面试工具”的因果，使企业感知社会责任与工具权益的绑定关系。雇主反馈等轻量数据可在本地或业务接口层保存，用于后续人工运营，不构成独立生成式子系统。

## 6.6 AI 模块测试、迭代与性能优化

功能测试覆盖多语言、多轮对话与链路契约。后端 pytest 包括简历归一化与增量润色、画像上下文、页策略与导出、面试程序阶段与自定义答案、互动题库队列、Planner 意图路由、Gap 核心与目标岗位上下文等用例；集成配置允许在具备密钥时跑真实 LLM 调用。前端侧以三大 demo 页联调为主，验证 SSE 进度、互动面试轮询、画像恢复深链与捐赠门禁。匹配分则在 Node 侧对技能重叠与加权边界做服务级验证。Planner 路由离线评测（规则夹紧层）可达较高链路一致性；跨 Agent 字段契约评测用于暴露偶发不一致，指导提示词与 JSON 契约收紧。与 RAG/向量检索相关的历史评测产物仅作实验归档，不作为当前生产能力验收依据。

弱势群体适配迭代主要体现在交互工程而非单独模型微调：将整份重生成改为澄清后增量润色；支持“仅岗位标题亦可启动”的柔性输入；输出强调短段落与可勾选行动项；对弱势群体账号免捐降低使用门槛。工程上还通过对话记忆压缩、模块并行润色、Redis 会话与 LLM 排队（限制并发）降低长尾超时与雪崩风险；简历生成流式化改善感知等待。多语种一致性方面，语言守卫与翻译模型分工减少“中英混杂”；导出与版式按语言切换进一步修正三地投递观感。后续优化方向包括恢复可控的 OCR/Embedding 以增强扫描件与细粒度召回，以及真正接线盲筛阅览接口——均需在开关与评测达标后再纳入生产叙事。

## 6.7 AI 模块创新点与包容性设计总结

本平台 AI 模块的创新不在于堆叠未启用的向量组件，而在于把**可编排多 Agent 职业助手**与**可解释包容匹配**嵌入大湾区弱势群体就业场景。技术上：其一，以 Redis/MySQL 结构化画像与目标岗位 meta 实现跨简历—面试—学习路径的上下文复用，显著降低重复输入成本；其二，以技能优先规则匹配软分与岗位包容硬筛形成公平导向，将敏感属性排除在软惩之外；其三，以主模型生成 + Hunyuan 翻译 + 语言守卫构成 zh / zh-TW / en / pt 一体化内容引擎，服务跨境投递。包容性上：分步澄清、轻量程序面试、可编辑学时时间线与免捐访问，降低银发与残障用户面对长文本与高门槛工具时的摩擦；输出侧重可执行建议与结构化字段，贴近辅助技术友好的阅读习惯。

相较市面通用招聘 AI（往往强调简历海投润色或单点模拟面试），本平台差异化在于：**同一画像驱动的三段式赋能闭环、捐赠绑定的企业 Premium 治理、以及面向弱势群体的访问与交互设计**。在诚实界定能力边界的前提下——承认在线 RAG/OCR/完整盲筛尚未作为生产默认路径——现有实现已形成可演示、可评测、可扩展的 AI 就业赋能技术底座，为后续向量增强与匿名初筛留下清晰接口与配置开关。
